# rhix_hello

Four independent modules use `rhix` typed containers. Each module creates its own Core, Device, Window and Queue; main only selects the module/backend and parses arguments.

```text
demo_rhix_hello --list
demo_rhix_hello --module hello_window --backend vulkan
demo_rhix_hello --module hello_triangle --backend d3d12 --frames 120
```

The positional backend argument remains supported. Without `--module`, a line-based terminal menu opens (also available with `--tui`). Enter a module number or name; invalid input retries, and `q`, `quit`, or EOF exits without opening a window. `--tui` and `--module` are mutually exclusive; `--backend auto` uses the default backend. Specify `--module` for unattended runs; omit `--frames` to run until the window closes. P switches requested VSync mode, Escape exits, and the title displays `grassland::FPSCounter` statistics.

- `hello_window`: original RGB (0.6, 0.7, 0.8) clear/presentation and supported presentation-combination output. D3D12, Vulkan and the existing Metal backend are supported.
- `hello_triangle`: D3D12/Vulkan/Metal colored indexed triangle on that background. The module creates independent GPU-only vertex/index Buffers, uploads once through CommandContext, finalizes a Slang Program, then records bindings, viewport/scissor and DrawIndexed. Resize/minimize/restore and P-mode changes are supported.

- `hello_cube`: the rotating colored cube from `graphics_hello`, with a fixed uniform-buffer BindingGroup and a D32 depth attachment. The depth image follows the window extent. Uniform uploads take a CPU snapshot and are ordered with draws on the same queue.
- `hello_texture`: the XOR texture triangle from `graphics_hello`, using a sampled image and linear sampler in a versioned BindingGroup.

The new modules and the depth/stencil, MRT and BindingGroup APIs are implemented on D3D12 and Vulkan. Metal is unchanged and currently supports only `hello_window` and `hello_triangle`; select those explicitly when using Metal.

## Shader and Program contract

Shader stores original Slang source, entry point and stage; creation does not compile it. Program captures shaders and the C++ vertex layout, owns their references, and compiles/creates the native pipeline at Finalize. After successful finalization it is immutable; repeated Finalize is a no-op.

`RHI_INPUT(location, type, name)` is expanded by a generated prefix into the C++ layout's Vulkan/Metal attribute locations or D3D12 input semantics. Source BOM is preserved by Shader and omitted only when concatenating the compilation input. C++ `PipelineLayoutDesc` and `BindingLayoutDesc` describe groups, binding numbers, resource types, fixed array capacities and shader visibility. Layouts are copied into Programs/Groups and remain fixed; group resources can be rebound. Generated `RHI_UNIFORM`, `RHI_STRUCTURED_BUFFER`, `RHI_RW_STRUCTURED_BUFFER`, `RHI_TEXTURE2D`, `RHI_RW_TEXTURE2D`, `RHI_SAMPLER` and corresponding `_ARRAY` macros use this layout. Resource macros take `(group,binding,type,name)`; sampler macros omit `type`. Arrays get their length from C++, not from reflection. Reflection checks used resources against the expected type, position, array count and stage; unused declarations may be eliminated.

D3D12 assigns b/t/u/s registers in binding order within each group/space, and uses separate resource/sampler tables. Vulkan preserves group/binding as set/binding. Programs also describe up to eight RGBA8/BGRA8 color outputs and an optional D32 or D24S8 depth/stencil format, depth compare/write, front/back stencil operations, masks and reference. Triangle-list topology and float/float2/float3/float4 vertex attributes remain supported; culling/blending and runtime-sized descriptor arrays are outside this change.

## Buffer and command lifetime

CreateBuffer returns a fixed GPU-only allocation managed by VMA, D3D12MA or private Metal storage. Backend Buffer bases expose resource access; AllocatedBuffer subclasses own allocations. Nested UploadPool::Lease subclasses forward access to pool-owned upload allocations; custom GPU-only resource pools can later implement the same interfaces without changing the public Buffer type. Each Device owns its allocator, upload pool and attachment pools; children borrow their Device.

CmdUploadBuffer copies CPU bytes immediately into an automatically leased upload Buffer, then records a native GPU copy. The caller can release/reuse the CPU data after the call. CmdCopyBuffer copies between distinct Buffers. UploadPool owns the physical AllocatedBuffers and returns backend Buffer-derived UploadPool::Lease objects. Leases forward the Buffer interfaces and mapped Write to the underlying storage, borrow their pool, and return occupancy on destruction of their last reference. CommandContext retains each lease through its ordinary resource table, with no separate uploads list or manual return path. Storage is recycled after GPU completion and final command reference release, or when an unsubmitted context is abandoned. Upload storage is grouped into independent power-of-two size classes starting at 64 KiB. Acquire takes an idle buffer directly from its class. Each class tracks allocated/occupied counts and a monotonic queue of occupancy changes over the last second; Release discards idle buffers above that recent peak. Equal occupancy samples keep the latest timestamp. Trimming occurs on returns to that class, without a background sweep. There is no per-frame reset or CPU wait per upload. Callers still order overwrites against prior GPU readers using queue ordering/dependencies.

CmdBindProgram precedes vertex-buffer and group binding. Bind all required vertex slots and groups again after changing Program. CmdBeginRendering selects an ordered color-attachment array and optional depth/stencil attachment, with independent LOAD/CLEAR/DISCARD and STORE/DISCARD operations (including separate depth/stencil operations); CmdEndRendering explicitly closes the scope. Draw calls require an active scope. Upload, copy, standalone CmdClearColor, Present and submission require no active scope. A scope may contain no draws (for example, a clear-only pass). RTV/framebuffer leases remain backend details. CmdDraw and CmdDrawIndexed support instancing and base offsets. Contexts retain the exact Program, Buffer and Image objects they use. Barriers are recorded immediately and used resources return to default states when submission ends recording.

D3D12 leases RTV slots from Device-owned heap pages. Vulkan prefers dynamic rendering when the negotiated Vulkan 1.3 core feature or Vulkan 1.2 VK_KHR_dynamic_rendering feature is supported. Program uses attachment formats instead of a RenderPass, and Begin/End record the corresponding core/KHR commands; the attachment cache creates only ImageViews. Otherwise, it uses traditional RenderPass/Framebuffer objects: render passes are cached by format and load/store operations, image views/framebuffers by ordered physical-image tuple. Load/store variants remain compatible with the same Program pipeline. Vulkan synchronizes vertex/index/uniform/shader reads and storage writes at scope boundaries so bindings can change inside a scope without splitting it. Swapchain teardown retires cached attachments after GPU idle, while completed contexts can finish returning their CPU leases. Dynamic rendering is not required.

Callers release child handles before parent Device/Core handles, and release old frame references/recordings before resize/rebuild boundaries. Device shutdown drains submitted work. Metal uses tracked private buffers/textures, shared upload leases and explicit render encoders. Bindings set outside a rendering scope are applied when the encoder begins; changes inside the scope are encoded immediately. Slang emits MSL, which Metal compiles at Finalize.

## Binding lifetime and descriptor pages

`CreateBindingGroup(layout)` allocates binding slots without initializing them. `BindResource(binding, resource)` writes one slot; typed vectors write arrays, with an optional `first_element` for partial updates. Buffers and images are retained, and sampler descriptions are copied. Use `BufferView{buffer, offset, size}` for a byte subrange; size zero selects the remaining buffer. Structured element stride is reflected from Slang during Program Finalize for the selected target, including structured-buffer arrays. Used bindings must agree on stride across shader stages. Binding failures leave the previous contents unchanged. All layout slots must be initialized before `CmdBindGroup`.

`CmdBindGroup` captures the current binding version, including its resources and descriptor storage. Later `BindResource` calls affect only subsequent `CmdBindGroup` calls, even before Draw or Submit. Unreferenced versions are updated in place; a captured version is copied only when changed. Commands keep old versions alive until canceled or retired after GPU completion. Vulkan allocates a new descriptor set on a fork; D3D12 versions own CPU-only descriptor ranges. Commands retain these versions without copying CPU descriptors at each bind, then copy changed tables into shader-visible storage at Draw. Structured-buffer tables are cached by the Program's reflected strides. Barrier tracking reads the captured resources. Buffer, Image and Sampler writes stay typed through native descriptor creation; the common resource records are snapshots only. Vulkan writes a contiguous binding-array update with one VkWriteDescriptorSet. Version cloning copies initialized runs through the corresponding typed path. These snapshots preserve bindings, not resource contents: updating pixels or buffer bytes still requires proper GPU ordering. CPU access to the same BindingGroup must be externally synchronized.

Uniform offsets must satisfy backend alignment (256 bytes on D3D12); D3D12 allocations must include the rounded 256-byte CBV range. D3D12 structured buffer offset/range must be multiples of the reflected stride; these checks occur at CmdBindGroup, where the Program is known. Vulkan uses its compiled SPIR-V element layout directly. Texture bindings accept independent color images; swapchain frames and depth sampling remain unsupported. Independent images automatically enable storage usage when their format supports it; RW texture bindings require that usage. Metal binding groups remain unimplemented.

`CmdUploadImage` snapshots complete RGBA8/BGRA8 rows with the supplied CPU row pitch, leases upload storage and records a GPU copy. It is allowed outside rendering scopes. Changing bindings within a scope is supported, but a resource must not simultaneously be an attachment and shader input, or be bound for conflicting read/write uses. Dependent storage accesses between draws require separate End/Begin scopes; this version does not add an in-scope barrier command. Bind texture groups outside a scope when transitioning from a different image use. Vulkan returns color targets to their default layout at EndRendering, permitting their use in a later scope.

D3D12 RTV, DSV, CBV/SRV/UAV and sampler pools allocate contiguous ranges from page-local rings. A range never straddles a page; wrap padding stays occupied until preceding leases return. Out-of-order release marks a range free, while the tail advances only through the released prefix. When a ring empties it resets; one normal idle page is cached, extra idle pages and oversized pages are destroyed. GPU resource pages use 4096 descriptors and sampler pages use 256; an oversized request gets its own page within native limits. Each CommandContext reserves shader-visible ranges and appends only changed tables. When one heap type runs out of space, all still-bound tables of that type move to a new range and both types of root tables are rebound. Earlier ranges remain alive through GPU completion. Unchanged tables are reused while capacity remains; CPU descriptor storage stays with the captured binding versions.

Vulkan groups own descriptor-set leases from pages of up to 64 sets, with fixed descriptor budgets. Allocation grows a new page on exhaustion/fragmentation. Final lease destruction frees the set; an empty page is reset, and only one idle page is cached. Group destruction also releases its views and samplers. Attachment views/framebuffers have their own leases. CommandContext holds groups and leases through its ordinary resource-use table; no separate descriptor return queue is needed. Submitted work keeps them alive until GPU completion and final command reference release; abandoning an unsubmitted context releases them too. Device/Core still must outlive their children.

## Vulkan rendering-path regression

With Vulkan SDK validation, API-dump and Profiles layers installed and a Vulkan 1.3+ GPU supporting dynamic rendering, run `python test/rhi/test_vulkan_rendering_paths.py <demo executable> [<second demo executable>]` from the repository root. With `--headless`, this runs all four modules; windowed mode runs the triangle. It checks native capabilities, a Vulkan 1.2 KHR profile, and a Vulkan 1.2 profile with dynamic rendering disabled. It verifies the actual native Begin/End commands and that dynamic rendering creates no RenderPass or Framebuffer objects. Profile simulation changes reported capabilities; it does not substitute for testing on older hardware.


Headless benchmarks (D3D12/Vulkan/Metal) render to independent 1280x720 RGBA8 images without creating a GLFW window, swapchain, or presenting. `hello_window` measures its clear pass; `hello_triangle` measures the same indexed triangle draw as the windowed scene. Each module independently creates its own Core, Device and resources.

```sh
demo_rhix_hello --headless --all --backend vulkan --frames 10000
demo_rhix_hello --headless --module hello_triangle --backend d3d12 --frames 10000
```

`--all` runs all four modules sequentially on the selected backend, continues after a failed module, and returns nonzero if any module fails. It cannot be combined with `--module` or `--tui`. Each scene prints its measured frame count, wall time and average FPS. Headless runs use 60 untimed warmup frames and at most 3 in-flight frames; target reuse and the final timing boundary wait for GPU completion. Setup, shader compilation, image initialization and initial uploads are outside the measurement. The cube's per-frame uniform update is included. This is end-to-end rendering throughput including CPU recording/submission and synchronization, not GPU timestamp duration. Use Release without validation layers for performance comparisons.

Without a positive `--frames`, headless runs measure 3000 frames per scene; windowed `--all` runs 300 frames per scene. Normal individual windowed demos remain interactive. `--all` selects scenes, not backends. Metal supports both independent-image benchmarks and windowed triangle rendering.

## Regression tests

Build `test_rhi` and run `ctest --test-dir cmake-build-debug/test/rhi --output-on-failure`. Set `LONGMARCH_RHI_WINDOW_TESTS=1` to include window tests, `VK_INSTANCE_LAYERS=VK_LAYER_KHRONOS_validation` and `VK_LAYER_VALIDATE_SYNC=1` for Vulkan validation. CTest runs each GoogleTest case in its own process. This also isolates the backends: on the tested Windows NVIDIA driver, globally enabling D3D12's debug layer and then destroying an acquired Vulkan window in the same process triggers an internal D3D12 destruction error, even without recording commands.

Pixel regressions cover MRT plus depth rejection, depth-only stencil writes preserved into a color pass, fixed uniform ranges, texture/structured-buffer arrays, group changes across descriptor pages, release before submission, and storage image/buffer writes read in a subsequent scope. Pool tests cover contiguous ranges, wrap padding, out-of-order release, oversized pages, descriptor-set reuse and idle-page trimming.
