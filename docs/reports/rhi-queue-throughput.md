# 离屏 Main / Assist 队列吞吐对比

测试日期：2026-11-10。结论：**重构后的 Main 吞吐总体接近旧版；Assist 并不是普遍的性能优化。**

在相同的两次提交结构下，RTX 5080 的 AS 更新出现收益：D3D12 +7.4%，Vulkan +4.2%。
但把准备和计算合并成一次 Main 提交后，收益分别缩小到 **+3.3%** 和 **约 0%**。
RTX 3090/Linux Vulkan 的全部测试中，Assist 都没有提升。其他负载多数持平或下降，
尤其小任务的跨队列同步成本明显。因此这些结果不支持默认将全部素材准备迁到 Assist；
更合理的比较基准应包含单队列合批，是否拆队列需要根据实际负载测量。

## 版本、环境和方法

- 旧框架：main `6ddcd48e`，即 PR113 之前。新框架：`aaac057c`，包括 Queue-owned Submission
  和共享原生队列能力修正。基准提交 `3d8990e7`；重射线运行脚本 `ba7e71ce`；合批对照 `e492798c`。
  基准代码之后没有修改框架实现来优化结果。
- 本机：RTX 5080 16 GB，驱动 617.42；Core Ultra 7 270K Plus；Windows 11 10.0.26300；
  MSVC 14.51.36231，Release `/O2 /Ob2 /DNDEBUG`；测 D3D12 和 Vulkan。
- Meshy-PC-3090：RTX 3090 24 GB，驱动 615.71.10；i9-11900K；Linux 7.0.0-38-generic；
  GCC 15.2.0，Release `-O3 -DNDEBUG`；测 Vulkan。
- **所有负载离屏，无 Window、SwapChain、Present 或人为延迟。** 同一 GPU 上没有同时运行两组基准。
  旧版与新版使用同一份 C++ 负载源码；`RHI_BENCH_LEGACY` 只适配队列枚举、Context 创建和 Submit API。
  标准及重射线源码统一换行后的 SHA-256 为
  `60407bf101cccf091512a22b5da199f397e783499eae8e836a863f3c7d4c854d`。
- 单 CPU 线程录制、提交；固定 **8 个独立在途槽位**。每槽有独立输入、输出、BLAS/TLAS；
  复用前等待上一任务完成。Assist 模式将准备阶段完成 Event 编入 Main 提交，不在两次提交间 CPU 等待。
  标准 Main 与 Assist 每帧均为两次提交；另有一次 Main 提交的合批对照。
- 每个进程先预热 32 帧。计时包含录制、上传快照、提交、槽位复用等待和最后的完成等待；
  不包含资源创建、Shader 编译、输入生成、最终下载和 CPU 校验。
  这是端到端吞吐，**不是 GPU timestamp 或纯 GPU kernel 时间**。
- 每个组合五次，固定随机种子 113，打乱工作负载及旧版/Main/Assist 顺序。
  共 **315 次正式运行，63 个组合，每组 5 次**；均成功退出，最后 8 个槽位的全部输出元素均通过校验。
  不将最终槽位校验描述成每一帧都有读回。正式计时关闭验证层；另行启用验证层进行了正确性预检。
- 表中吞吐为五次的中位数，单位为逻辑帧/秒（计算批次/秒，不是显示帧率）。
  相对变化为两个中位数之比减一；最右列为同轮配对变化的最小值～最大值，未丢弃慢样本。
  没有锁定 GPU 时钟，遥测只在各进程前后采样，不能代表整个计时区间的频率或占用率。
  五次结果描述本次测试的波动，不作为普遍性能保证或正式显著性检验。

## 工作量

| 案例 | 每帧准备 | Main 消费 | 测量帧数 |
|---|---|---|---:|
| 上传小任务 | 上传 65,536 个 uint，256 KiB | 每元素 8 次整数递推 | 32,768 |
| 上传＋计算 | 上传 1,048,576 个 uint，4 MiB | 每元素 256 次整数递推 | 16,384 |
| AS 重建 | 上传 4.5 MiB 顶点；重建 131,072 三角形 BLAS 和单实例 TLAS | 512×512 像素，每像素 8 条 ray query | 4,096 |
| AS 更新 | 同样上传；更新允许更新的未压缩 BLAS/TLAS | 同上 | 8,192 |
| 重射线 AS 重建/更新 | 准备量不变 | 每像素 64 条 ray query | 2,048 |
| 合批对照 | 同 AS 更新 | 每像素 8 条 ray query；Main 合并为一次提交 | 8,192 |

输入在每个槽位复用时交替变化；AS 几何的 Z 坐标实际变化，不能通过只更新静态数据蒙混校验。
计算输出与 CPU 整数递推比对；ray query 命中距离与两组几何的解析距离比对。
AS build/update 使用各自适合的创建标志，因此应横向比较同一行的队列安排，不将不同行当作等量操作。

## 合并 Main 提交后，收益是否还存在？

这一组重新轮换测量相同的 AS 更新负载。旧/新 Main 均将上传、BLAS/TLAS 更新和 ray query
录入同一 Context，只提交一次；Assist 仍使用准备/消费两次提交。这样既减少提交次数，
也可能减少 Context 边界的状态恢复，属于实际应用可以采用的单队列写法。

| GPU / API | 旧 Main 合批 | 新 Main 合批 | Assist | 新合批 / 旧合批 | Assist / 新合批 | 配对 Assist 变化范围 |
|---|---:|---:|---:|---:|---:|---:|
| RTX 3090 / vulkan | 1498.4 | 1495.7 | 1382.1 | -0.2% | -7.6% | -7.8% ～ -7.5% |
| RTX 5080 / d3d12 | 2813.3 | 2824.6 | 2917.3 | +0.4% | +3.3% | +1.6% ～ +4.5% |
| RTX 5080 / vulkan | 2818.3 | 2866.3 | 2866.3 | +1.7% | +0.0% | -0.2% ～ +0.9% |

因此，5080 D3D12 在这个 AS 更新负载下仍有小幅、五轮均为正的收益，但实际优势约 3.3%，
不能只报告相对两次 Main 提交的 7.4%。5080 Vulkan 的优势在合批对照中消失。
3090 Vulkan 相对合批 Main 仍约慢 7.6%。

## 适用范围与解释

两个 API 队列不等于两套独立计算资源。当前 D3D12 使用 DIRECT 队列，Vulkan 使用同一个
 graphics+compute 队列族；这不是专用 COPY 队列或独立 transfer-family 的测试。
更多 GPU 工作重叠可能带来资源竞争，额外提交与 Event 等待也有成本。
这些是解释方向，而非本次已通过 GPU profiler 证明的瓶颈；本次直接证据是吞吐和结果正确性。

本次场景是规则三角网格、单实例 TLAS、整数计算、单 CPU 提交线程及固定 8 槽流水线。
不能据此断言任意场景拆队列都会更慢，也不能将小幅正向结果推广为整个框架的普遍加速。
本任务没有改动同步实现或队列策略去追求某个分数。
